The Core Shift — Multi-Tenant Marketplace

BEFORE (single vendor):
  Your warehouse → products → customers

AFTER (multi-vendor):
  Your warehouse   ┐
  Distributor A    ├── products → customers
  Distributor B    │
  Distributor C    ┘
Every product, order, inventory, review, and payout now has a seller_id attached.

- product review  (this item quality)

Full Technology Stack — Why Each One
Message / Event Layer
Technology	Purpose	Where Used
Kafka	Event streaming — things that HAPPENED	order.created, order.paid, delivery.checkpoint, inventory.reserved — high volume, fan-out, replayable
RabbitMQ	Task queues — things that NEED TO BE DONE	Send email, process payout, resize image, retry failed jobs — one-time work, easier DLQ/retry
Redis Pub/Sub	In-process fan-out within a service	Chat WebSocket rooms — broadcast message to all connections inside chat-service

Rule of thumb:
Kafka  = "this event happened, who cares?"  (broadcast, replayable)
Rabbit = "do this job exactly once"         (task, retry, delay)
Redis  = "push to live connections now"     (ephemeral, in-memory)
Realtime Layer
Technology	Purpose	Where Used
WebSocket	Bi-directional realtime	Chat messages, live delivery map tracking
SSE (Server-Sent Events)	One-way server push	Order status updates, notification bell, stock alerts — simpler than WS

WebSocket = customer sends + receives  (chat, driver GPS upload)
SSE       = server pushes only         (order status bar, notifications)
Storage Layer
Technology	Purpose	Where Used
PostgreSQL	Primary data store	All 18 services — each has its own DB
Redis	Cache + sessions + rate limiting	API gateway rate limit, cart, token blacklist, online presence
Elasticsearch	Full-text search	search-service — product search across all sellers
S3 / MinIO	Object storage	Product photos, KYC docs, review images, delivery proof photos
Internal Communication
Technology	Purpose	Where Used
gRPC	Synchronous service-to-service	order-service calls inventory-service to check stock before accepting order
REST	External client API	All public endpoints via api-gateway

gRPC = internal, typed, fast (Go generated clients)
REST = external, browser/mobile friendly
Observability

Prometheus	Metrics collection
Grafana	Dashboards — orders/min, Kafka lag, delivery SLA

Kubernetes	Production deployment

Vault	Secrets management (DB passwords, API keys)

What Interviewers Will Ask You (and you must nail)
These are the real senior backend questions:


"Walk me through your order saga."
→ You explain orchestration vs choreography, why you chose orchestration,
  the compensation table, the outbox pattern. ADR-0004 is your answer.

"What happens if your service crashes between DB commit and Kafka publish?"
→ You say: "That's exactly why we use the transactional outbox —
  we write the event to an outbox table in the same transaction,
  a relay publishes to Kafka. The event is never lost."

"How do you prevent double-charging a customer?"
→ Idempotency-Key header + outbox + payment provider idempotency key.

"How do you guarantee a parcel's timeline is in order?"
→ Kafka partitioned by tracking_no — all events for one parcel
  go to the same partition, so they're strictly ordered.

"How do you handle the last-unit inventory race condition?"
→ SELECT FOR UPDATE on the stock row inside ReserveStockTx.

"Why 6 bounded contexts instead of 18 services from day one?"
→ ADR-0002. Distributed monolith risk. Modular monolith first.
If you can answer all of those fluently, you get the offer.
